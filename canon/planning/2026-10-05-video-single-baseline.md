# Single H.264 baseline

Cookbook decision superseding `2026-10-05-modern-codec-comparison.md`. Documentation only; no runtime change, new encode or rerun. Preserve exploratory run37265792670 and its actual successes/failures as evidence; it does not select a production codec. The compatibility-first order below supersedes any implication that further encoding should precede compatibility screening. The project charter and the rolling three-year hardware AND browser-release target remain unchanged (approximately October2023 onward at this decision).

## Decision and evidence

Current decision: H.264 ONLY. Close the modern-codec experiment workstream for now and defer optional-codec investigation. Do not generate or publish HEVC/AV1 delivery outputs, implement codec selection or fallback logic, retain extra production variants, or run more benchmarks. Preserve existing historical experiment evidence without promoting it into delivery. Focus current work on reliable single-baseline delivery and reusable verified cache. HEVC fails the sole-codec target and AV1 is not universal; possible benefits on a supported subset do not justify the additional storage, CPU and implementation complexity under the user's current decision.

Chromium's official list explicitly makes HEVC hardware-dependent. Mozilla's HEVC support tracker records Windows support from Firefox134, macOS136, and Linux/Android137. The official Firefox134 release notes date the Windows hardware-accelerated introduction to January7,2025; Firefox136 notes add macOS support on March4,2025. Inference: those later introductions leave browser releases within the October2023-onward target unsupported, so a universal HEVC-only route fails before bitrate or speed comparisons. [Chromium](https://www.chromium.org/audio-video/), [Mozilla platform status](https://bugzilla.mozilla.org/show_bug.cgi?id=1842838), [Firefox134](https://www.mozilla.org/en-US/firefox/134.0/releasenotes/), [Firefox136](https://www.mozilla.org/en-US/firefox/136.0/releasenotes/).

WebKit's Safari17 announcement limits AV1 to devices with hardware decoding support and gives iPhone15Pro/ProMax as examples. Inference: a Safari version or recent hardware release date alone cannot establish AV1 support across the target. Do not extrapolate model age, OS freshness, or one desktop browser success into a decoder guarantee. [WebKit17 AV1](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/#av1).

These sources establish concrete exclusions, not an exhaustive certification of H.264 on every browser build. Keep the existing qualified H.264 profile/container/audio path and retain its actual target-device checks. Separate video codec, profile/level/bit depth, MP4 tag/container, audio codec, browser/OS build and hardware decoder in the matrix; a codec name alone is insufficient.

## Gate for any future reopening

There is no next codec benchmark or conditional-codec implementation in the active plan. Reopen only when a concrete use case demands it and its expected benefit justifies compatibility, CPU, storage and maintenance costs. A calendar date, newer codec release or automatic benchmark schedule is not a reopening trigger; no additional permission gate is implied beyond this use-case requirement. If reopened, screen compatibility against the unchanged target first, identify a justified delivery role and actual device proof, then propose at most one bounded comparison before judging quality, useful latency, bytes and total cost. Capability hints alone are not playback proof; newer codec names alone do not establish value.

This supersedes the earlier modern-codec proposal's planned conditional follow-ups and any implication that HEVC/AV1 selection or H.264 fallback logic should now be implemented. H.264 is the sole current delivery path, not one branch of a new codec chooser. No progressive-delivery, audio-format, pass-count or architecture change is authorized here. Existing cache-ownership repair continues independently. Preserve run37265792670 and all previous receipts as historical exploratory evidence only; no rerun or additional benchmark is scheduled.
