# One optional 320p FIA comparison

> Measure one retained-source320p H264/AAC candidate and an Opus Low listening reference, without adding a supported preset. Keep the existing Small AAC treatment until actual listening verifies the user’s Low-quality floor; report size, detail and timing separately.

## Summary

Test one retained a13 recording at 320p, seeking a file smaller than the existing 224p bundle while preserving more useful teaching detail. This is an experiment, not a promised quality improvement or a fourth supported offering. Small480, Medium540 and Large720, their routes, cache identities, UI and existing qualifications remain unchanged. Do not block the current FIA repair or whole-page release.

## Existing implementation and feasibility

The current repository has closed size contracts in `container/video-contract-small.json`, `container/video-contract-medium.json`, `container/video-contract.json`, selected by `src/lib/video.ts` and the existing container adapter. Small is 854×480, H.26450fps, two passes, nominal200000 video bits/s, AAC42667bits/s mono48kHz. Medium uses253125 video bits/s at540; Large class is450000 at720 (actual requested439024). These are the same quadratic class curve: 450000×(height/720)^2. Public parsing deliberately rejects arbitrary dimensions and additional sizes; 320 is not currently supported.

Use a separate manual experiment alongside the existing `experiments/video-audio`/video comparison workflow pattern. Build the same pinned encoder image, invoke FFmpeg privately with an explicit experimental argument record, and reuse retained source bytes. Do not alter production contract selection, parser, MCP schema, worker routes or adapter identity merely to perform this comparison. The experiment is not a test of a deployed320 route.

## Hard audio-quality floor

The actual audio showcase uses voice Opus recipes from `container/recipes.mjs`. Current Low is `-ac 1 -ar 8000 -c:a libopus -b:a 8k -vbr on -application voip`, Ogg Opus. Medium is16k mono/16000Hz input/application audio; High32k mono/24000Hz input. Opus's reported48000Hz decode rate is not its input bandwidth. `src/demo-audiobench.html` deliberately explains that distinction.

The user requires audio quality no worse than this **current Opus Low treatment**, not a numeric8kbps floor across codecs. AAC and Opus rates are not interchangeable. Keeping existing Small AAC settings does not prove this requirement either. For a fair same-content listening reference, reuse a hash-pinned existing a13 Low output if available and proven generated by the exact recipe; otherwise the single authorized experiment may produce exactly one audio-only Opus Low reference from the same retained HQ source. That reference is an explicit second audio-only encode, not another video candidate. No remote provider, TTS, origin fetch or silent fallback. If the source contains meaningful stereo information, document the mono limitation and do not claim general suitability for other recordings.

Decode both candidate AAC and Low reference; record duration/start timestamps and seek/A-V alignment. Compare their audio on the same excerpts, including quiet speech and any background sound, with actual listening. Accept only if speech/meaning is not worse than Low; report the listener and excerpts. If uncertain or worse, the experiment remains unqualified: no automatic bitrate increase/retry or claim based only on bitrate. Any later AAC reduction or Opus-in-MP4 candidate requires its own bounded treatment and compatibility review; this proposal does not change the H.264/AAC baseline.

## Bounded execution and evidence

One manually dispatched reviewed commit, no automatic push/PR/main encode. At most one two-pass320 video output and, only if needed, one same-source Low audio reference. Retained source only; no network during encode. Video encode/mux300s total, optional audio reference120s, whole job10min including probes/captures, no retry. Source/output each60MiB maximum; pass logs32MiB each/64MiB aggregate, stderr64KiB, whole host-plus-active-container working set384MiB. Supervisor must reserve and account for temporary container files as well as retained outputs, stop owned processes on deadline, preserve failures and verify cleanup. Export at most12JPEG frames,2MiB each. Do not launch work whose remaining time/storage budget cannot fit its worst case.

Record source/output hashes, full actual codec/duration/frame decode, actual video/audio payload and mux overhead, exact encoder identity, pass1/pass2/encode times, source acquisition0, and cleanup. Encoder timing is a same-runner observation, not Cloudflare delivery speed. Preserve a measured video-rate miss above5% as rejected-budget; no tolerance widening or rate-search loop. Duration must remain within250ms of source and audio/video start/duration differences must be reviewed.

Review matching decoded10/40/70s frames and motion at the same phone/display sizes for source, compact and320. Check scene correspondence, river/foliage teaching detail, blocking, movement and playback/seek/A-V behavior. Browser playback may use retained local bytes with that scope explicit. Full-motion/acoustic/device evidence must not be inferred from stills or successful decoding. Report whether the one measured file is smaller than compact and where it looks better, worse or indistinguishable. Neither a higher raster nor a smaller file alone is success.

## Result and reversal

Publish the measured experiment separately; no automatic addition to the comparison page or presets. A whole-Bible pack estimate may multiply measured bytes-per-minute by an explicitly hypothetical duration, clearly excluding other media/pack overhead. One79sriver recording cannot establish a universal whole-Bible budget or quality result. Keep the three core offerings unchanged unless the user subsequently chooses an experimental result for product work. Reversal is to retain the evidence and remove no existing capability.
