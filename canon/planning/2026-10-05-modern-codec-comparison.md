# Modern codec and time-to-first-frame: smallest next comparison

Status: private cookbook proposal, superseding implementation of the paused H.264 subq1 micro-tuning experiment. Preserve that draft and earlier H.264 evidence unchanged. No encoding, download, runtime or delivery change. User permits single-pass when it improves useful playback latency; two-pass is no longer an unconditional requirement for the next candidate.

## Compatibility and CPU evidence

Compatibility target: both phones/hardware released and browser releases from the preceding three years, a rolling window (approximately October2023 onward for this decision). A recent browser release or OS version does not establish the phone’s hardware decoder. Select delivery using actual device/browser codec capability checks followed by real playback validation; retain H.264 fallback when the chosen modern codec is unsupported or fails. Do not infer universal AV1 support from this date window.

WebKit documents AV1 playback on devices with hardware decode support; iOS27 alone does not identify that hardware. HEVC is a plausible Apple-target candidate, not permission to assume every installed PWA/device will decode it. Chromium's own supported-codec list makes HEVC hardware-dependent. Record exact device model, OS/browser, actual codec string and MediaCapabilities decodingInfo supported/smooth/powerEfficient hints, followed by real playback/seek/offline testing. Hints and desktop Chrome are not physical iPhone proof. Retain the qualified H.264 fallback until actual target acceptance. [WebKit17](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/), [WebKit17.4](https://webkit.org/blog/15063/webkit-features-in-safari-17-4/), [Chromium codec support](https://www.chromium.org/audio-video/).

FFmpeg exposes libx265 and libsvtav1 only when compiled with those libraries. Verify actual installed encoder help/build first. x265 presets trade CPU work against compression efficiency; preset names across x264/x265/SVT-AV1 are not equivalent quality or speed. No general CPU-time multiplier, quality-equivalent savings percentage, or universal AV1 recommendation follows from documentation. Measure on the same CPU allocation/runtime. [FFmpeg codecs](https://ffmpeg.org/ffmpeg-codecs.html), [x265 preset semantics](https://x265.readthedocs.io/en/stable/presets.html).

## Latency, size and quality are separate measurements

Record each pass, total encode and end-to-end complete-artifact time, actual video/audio/mux bytes, rate, cadence, codec and complete duration. Keep identical AAC payload/sample/timing checks; inspect HEVC decoded source/A/B frames and motion at480display size,720diagnostic size, cuts and long-GOP seeks. Apply existing nominal-rate and matched-payload checks; if single-pass misses the match, disclose it and do not claim matched-budget quality equivalence or silently correct it. Lower file size is not automatically better quality efficiency.

Record **time to first decoded frame**, not only first network byte, in a separate actual browser measurement. The current faststart MP4 response is produced after complete encoding and full verification; moving moov to the front does not turn this service into progressive encoding. For this first pair, TTFF includes complete-file production and delivery. Measure server request→first byte, first byte→metadata/frame, and total encode separately on a stated network/cache state. No claim that B already streams before completion.

## Conditional progressive-delivery follow-up

If HEVC decode/quality/time is acceptable, next test one streaming mode within the existing proxy: single-pass encoder output into a streamable fragmented MP4, bounded tee/final artifact, backpressure, disconnect-independent owner and verified final cache. The present whole-file SHA gate cannot validate every final byte before progressive playback; the cookbook must explicitly separate provisional streaming integrity from final verified offline/cache readiness. Fragment flags/keyframe cadence, init segment, browser/MSE/native support, seek/range behavior and partial-output failure need a concrete reviewed contract before implementation. Long30s GOP may make fragment emission too sparse; do not silently shorten it or equate first-byte emission with playable frames. [FFmpeg MOV/MP4 muxer fragmentation documentation](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv).

AV1 is conditional on actual target decode capability and an acceptable measured CPU/latency budget. It is not an automatic third encode in this A/B. No new architecture, delivery option, production codec default or universal iPhone claim follows from this proposal. Preserve H.264 fallback and the existing ownership repair independently.
