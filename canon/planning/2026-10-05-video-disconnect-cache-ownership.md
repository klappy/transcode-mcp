# Complete accepted video work after a viewer disconnects

Status: private cookbook proposal; supersedes the disconnect-triggered cancellation proposal. No runtime changes. User direction is to finish bounded accepted work and seed reusable cache. Playback Stop, navigation, network loss, and closing a page detach that consumer; they do not cancel the underlying transcode. An explicit job-cancellation interface is outside this slice.

## Evidence and smallest change

The current Worker selects a random existing container Durable Object, fetches encoder identity, checks R2, and on MISS owns encode response consumption, hash verification, quarantine and canonical publication. A disconnect can therefore abandon useful work even when FFmpeg completes. The four-CPU development proof completed encoding in about53seconds; Worker waitUntil's30second post-disconnect allowance does not guarantee that completion, much less the existing600second job envelope.

Move ownership of that existing video MISS operation and its verified publication into the existing AudioContainer Durable Object class. Keep the same container, five-slot namespace, approved source contracts, FFmpeg process, R2 bucket and validation routines. Do not introduce another service, queue, public job endpoint, credentials inside the FFmpeg container, or durable unbounded job registry. Audio/image behavior stays unchanged.

For the current compatibility date2025-05-01, enable durable_object_io_tasks_prevent_eviction in development. Cloudflare's October1 documentation says registered pending I/O work prevents Durable Object eviction for up to15minutes per operation. Register the complete bounded operation with the existing DO context waitUntil immediately when accepted. Its600second outer deadline, including transfer/verification/publication/cleanup, remains below that protection. This is bounded platform lifecycle support, not guaranteed execution through crashes or deployments. Worker waitUntil alone is not the solution.

Sources: https://developers.cloudflare.com/changelog/post/2026-10-01-pending-io-keep-alive/ and https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil .

## Ownership and sharing contract

Route video requests deterministically to one of the existing five DO slots using a stable hash of the validated source identity plus recipe contract. This routing identity is not the output cache identity. The canonical cache key continues to include the actual verified encoderRevision and the complete existing contract. Audio keeps its current routing.

The DO accepts only the already allowlisted video request shape. At its orchestration entry, synchronously insert one in-flight owner promise keyed by source plus contract before any asynchronous encoder-information lookup. This admission key coalesces concurrent identical requests during identity resolution; after resolution, the actual encoderRevision-bound key governs cache lookup and publication. Pin that encoder identity for the entire operation and require the transcode response to match it. Do not carry an owner across deployment or treat a source-only key as canonical output identity.

Use one active video owner per existing container slot, matching its existing single-video capacity. Identical requests join that promise. A different MISS while the slot is occupied receives the existing bounded busy failure rather than an unbounded waiting queue. Clear ownership in finally only if it still refers to that exact owner. Failed work is not a ready cache result. Concurrent lookup and owner creation must not race into two encodes.

The owner deadline is independent of every consumer Request.signal. Once accepted, register the owner with DO waitUntil and retain consumption of the container response through existing length/hash validation, private quarantine, verified canonical publication and cleanup. SDK inflight protection requires retaining that response consumption; never cancel its reader because one viewer left. The job's own deadline and real validation/encoder failures still abort work and remove quarantine. Keep current no-publication-on-corruption guarantees.

Each waiting consumer may abandon its own wait or response without aborting the owner or another consumer. On success, each remaining consumer opens its own fresh R2 body, using existing HEAD/range/status semantics. Never share a consumed response stream among joiners. A late request can read the completed canonical object. There is no automatic repeat encode after failure; a later explicit request may retry within the existing bounded policy. A DO restart loses in-memory singleflight; exact canonical identity and quarantine validation remain mandatory, and no durable exactly-once claim is made.

## Scope and operational limits

Proposed owned paths: src/worker.ts existing DO class/video routing; src/lib/video.ts extracted/reused orchestration and serving helpers; narrowly focused video tests; development compatibility flags. container/video.mjs and encoder settings remain unchanged unless a separately reviewed concrete necessity is found. No app, audio/image route, source contract, cache-key weakening, idle setting, or production flag change in this slice.

Current cache HITs still resolve encoder identity and can wake a container. Preserve correctness now. A release-pinned identity or version-bound persistent identity index is a separate reviewed optimization; never trust an unversioned stale pointer. Likewise, a development-only60second idle window is a plausible follow-up based on SDK inflight response accounting, but it is not bundled here. No batching delay is added to Play. Deterministic sharing reduces duplicate same-source work; it does not promise parallel execution of different sources in one slot. This is a bounded initial ownership repair, not load-aware scheduling: five is the existing configurable capacity cap, not a requirement to keep five instances running, and different keys may still wake different cold slots. Queue a separate minimal dynamic-admission follow-up for warm-instance reuse, additional capacity only on concurrent demand, idle sleep, and an explicit configurable cost cap. Do not report those behaviors as implemented by this repair.

## Required proof and release gates

Focused tests must prove: two simultaneous identical requests cause one encoder dispatch; a departed consumer cannot abort the owner; a second consumer receives an independent readable body; a subsequent request uses the exact canonical cache result; different work receives bounded busy behavior; failed/corrupt/oversize output never becomes canonical; timeout cleans quarantine and frees only its own slot; stale finally cannot clear a newer owner; request signals do not enter owner fetch/verification; HEAD/range and audio/image behavior remain unchanged. Verify waitUntil registration occurs before the owner can outlive the request and that the registered promise includes publication and cleanup, not only encode.

Actual stable development proof: confirm exact deployed build and flag, begin one cold approved request, observe actual work, disconnect that viewer while substantial work remains, then observe natural bounded completion, verified canonical R2 bytes/hash, and a subsequent HIT with no second encode. Record the original disconnect as expected consumer behavior, not failed cancellation. Include concurrent joiner/read and independent response range checks. Preserve the earlier cancellation evidence as superseded-policy evidence. No rollout during the active proof. Existing actual source/output/browser qualification gates still apply; no output identity is fabricated and no production promotion follows from unit tests alone.

Rollback: revert the DO ownership/routing and development flag as one reviewed change, preserving canonical objects only under their existing exact identity. Keep failure receipts. Any ownership or corruption gate failure holds promotion.
